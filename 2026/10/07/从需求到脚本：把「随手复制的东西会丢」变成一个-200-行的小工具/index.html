从需求到脚本：把「随手复制的东西会丢」变成一个 200 行的小工具

Android 上有个很隐蔽的习惯性挫败感：你复制了一段东西，三分钟后想用，它没了。

不是真的没了——是剪贴板只有一个槽位，下一次复制直接覆盖。验证码、临时密码、快递单号、刚查到的 API 返回片段，这些东西的保质期往往只有几分钟，偏偏人的记忆比想象中短。

我试过各种”笔记 App 临时粘贴一下”，都觉得别扭：多一次切换、多一次输入框跳转，还可能把私密内容同步到云端。于是我决定干脆自己写一个。需求小得不能再小，过程却意外地能展开——这篇文章复盘整个过程，包括几个我一开始想错了的地方。

第二步：手动太啰嗦，改成自动

用了两天就嫌麻烦了——毕竟”手动点一下”和”复制完就走”之间，还差一个肌肉记忆。于是想改成：剪贴板一变，自动存。

Android 10 之后，普通应用读剪贴板有系统弹窗、有频率限制，纯 Termux 侧轮询会被系统挡回去。这就是我遇到的第一道坎。解法有两条路：

  • 用 Shizuku（rish 通道）以 shell 身份执行，可以正常读剪贴板；
  • 部分机型有临时 root（su），更省事。

于是需要一个 Java 小程序，用 app_process 直接跑在系统里，纯反射去调 android.content.ClipboardManager。这一步我没写多少业务代码，真正花时间的是权限和生命周期：

classes.dex 我故意放在 SD 卡而不是系统临时目录——否则 Android 的清理机制会某天早上悄悄把它删掉，然后你就得到一个”昨天还好好的”工具突然失效。

第三步：脚本最难的部分是”活着”

写到这一步，功能已经能跑了，然后我立刻掉进了后台进程管理的坑。

第一个坑是 toast 提示。watcher 是以 shell/root 身份跑的进程，它调不动 Termux 私有的 termux-toast——UID 不一样。于是我写了一个 Termux 侧的”提示循环”，去 tail watcher 的日志文件，发现新增的保存行就弹一次 toast：

那行注释就是我被这个 bug 教育出来的：文件被清空之后计数器不重置，提示会永久消失。这类”看起来能跑、其实已经死了”的静默失败，在后台脚本里几乎无法靠肉眼发现，只能靠这种注释提醒未来的自己。

第二个坑是脱离进程组。通知按钮的 action 是由系统用 dash -c 拉起的，父进程一秒后就退出，如果 toast 循环挂在原进程组里，会跟着一起被清理。解法是 setsid nohup 完全脱离，并且由内层 bash 用 $$ 写回真实 PID——因为 nohup 外层的 $! 和真正干活的 PID 并不一致，我曾经对着错误的 PID 杀进程，怎么杀都杀不掉。

第三个坑是重复启动。要开监控时得先确认 watcher 是否还活着，is_running 里不能只 kill -0：Termux 侧根本看不到 shell uid 进程的 /proc（hidepid），必须经特权侧探测。清理残留进程时也不能图省事用 pkill -f，那会连自己一起杀掉；正确的做法是 pgrep 收集明确的 PID 列表再逐个 kill。

第四步：随手写下的几行，也是最重要的

回头看，这工具一共就三个脚本：保存、监控、通知。真正花时间的不是逻辑，而是边界情况——权限掉线、进程被杀、日志轮转、PID 失配、dex 被清理。

所以如果你也想动手写点自动化小工具，我总结成四句：

  1. 先写最小可用版本并真的用起来，别在写第一版时就追求完整架构。
  2. 触发方式比功能本身更重要。点一下通知能省的事，和敲一串命令省的事，是两个量级。
  3. 后台进程的敌人不是 CPU，是静默失败。加日志、写状态、留注释，比优化性能重要得多。
  4. 用现成通道，别跟系统硬碰。Shizuku / 临时 root / app_process 这些”绕后门”的思路，比逆向硬刚限制要省下几个晚上。

脚本的全部代码在 ~/clip-saver/，结构很简单：bin/ 放三个脚本，clipboard_helper/ 放 Java 源码和编译脚本，compile.sh 负责把 .java 打成 classes.dex。想改的话，只需要有 openjdk 和 d8，pkg install openjdk-21 d8 一条命令就够了。

写在最后

现在我的复制板历史是一个纯文本文件，每天自动累积几十条。某天需要找回三天前复制的那个 shell 命令，我 grep 了一下就找到了。

这种”用几小时换来的确定性”——我认为是折腾 Termux 最值的部分。
