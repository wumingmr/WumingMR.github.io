网络连不上时到底该看什么：ping、traceroute、tcpdump 三板斧

写作注释: 本文由 AI 生成, 主题「网络排错三板斧: ping/traceroute/tcpdump」, 内容仅供参考, 欢迎留言交流。

排查网络问题最折磨人的地方不是「修不好」，而是「不知道该修哪儿」。DNS 挂了、路由绕路了、防火墙静默丢包——现象可能都是「打不开网页」，但根因完全不同。

好在终端里有三个命令，就能把一条网络链路切成几段，逐段判断问题出在谁身上：ping 定连通性、traceroute 定路径、tcpdump 定报文。顺序不能乱，因为它对应的正是那条自下而上的排查链。

第一斧 ping：先确认「到底通不通」

ping 测的是 ICMP 回显，能回答一个问题：这个 IP 到底有没有回应。

一次 ping 有三种典型结局：

现象 含义
有回复 网络层通，继续往上层查
100% packet loss 到这个 IP 的路径断了或被静默丢包
ping: unknown host 不是网络问题，是 DNS 解析问题

**关键技巧是对比着 ping。**先 ping IP，再 ping 域名，两者结果不同就锁定了问题层级：

IP 通而域名不通，说明 DNS 有问题，可以指定 DNS 服务器对照测试：

手机上还要留意一点：**ping 不通不等于服务不可用。**很多服务端默认禁 ICMP，这时 ping 全丢但 HTTP 照样能访问。所以 ping 只是排除法里的第一棒，不是判决书。

第二斧 traceroute：看清数据包走的哪条路

traceroute 的原理是逐跳发探测包，看哪一跳开始超时。它给出的是路径，而 ping 只给出终点。

读输出时重点看第一个持续丢包的跳：

第一跳（网关）正常，第四跳开始丢，但第五跳又通了——这说明中间那一跳只是不回 ICMP，不代表它断了。大量运营商设备都过滤 ICMP，中途跳不通是常态。真正有意义的信号是：从某跳开始一直到终点全丢。

如果 UDP 通而 TCP 443 被丢，说明防火墙拦的是 TCP 而不是整条链路。

第三斧 tcpdump：看看报文到底发了没有

前两斧只告诉你路径状态，tcpdump 能给出最硬的证据：线上实际流动的字节。参数很少，-i 网卡、-n 不解析、host/port 过滤：

三个值得记住的观察点：

1. SYN 一直发、没有 SYN-ACK 回来 —— 连接被丢包，或中间有防火墙静默拒绝。

2. 收到 RST —— 对端明确拒绝了，最常见的原因就是服务没监听那个端口。本地可以自己查：

3. 只有本机发出、包没上线路由 —— 应用层或本地网络配置问题，跟上游无关。

在 Termux 上抓包需要相应权限（Android 9 以后通常要 root），并且优先用 -i any，因为 wlan0 在不同机型和状态下名字会变。

一次请求会依次完成域名解析、TCP 连接、TLS 握手、发送请求，任何一阶段的报错都会明确打印出来。常常定位到这一步就结束了，根本用不着抓包。

几个配套的经验：

  • 先分层再抓包。 盲目抓包容易在几百行输出里迷路，先用 ping 和 traceroute 把范围缩到可疑链路。
  • 抓包前想清楚过滤条件，否则抓下来的东西自己都看不动。写不出 -nn 过滤式，往往说明当前怀疑点还不够清晰。
  • 别把「ping 不通」当结论。 ICMP 只是一个探测手段，服务端禁它是常态。
  • 一次只改一个变量。 同时换 DNS、换网络、改路由，出问题时反而无从归因。

这三个命令加起来不到一百字节，却是绝大多数网络问题的一线诊断工具。真正省时间的不是命令本身，而是心里那条自下而上、逐段排除的顺序。

总结

ping 告诉你通不通，traceroute 告诉你走的哪条路，tcpdump 告诉你线上到底发生了什么，再配一个便宜好用的 curl -v。从「网页打不开」到「根因是目标 TCP 443 被静默丢包」，通常只需要几分钟。把这条链练成肌肉记忆，排网络问题就不再靠运气了。
